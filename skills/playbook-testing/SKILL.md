# Playbook 测试工作流

将“验收标准 → 用例与风险 → 快速反馈 → 合并门禁 → 部署验证 → 生产反馈 → 回归保护”落实到用户指定的仓库。复用其语言、测试框架、脚本与流水线；只建设当前任务需要的阶段。

核心职责是决定项目各部分该测什么、在哪个阶段测、怎样触发及何时能够放行。init/plan 先按 [测试动作决策](references/test-actions.md) 从验收目标和风险给出模块与阶段矩阵，再补建缺失测试并接线。已有测试属于输入，不决定测试范围；没有测试的新项目同样需要适用的建议和实现。init 在项目 TESTING.md 或已有同类计划中记录策略与落地状态。

本技能提炼微软 ISE Engineering Playbook 的测试原则；hook 分配与证据契约是工程化建议，不是微软官方 hook 实现。本插件已包含共享执行器与 Codex hooks；新项目通过 [setup](../setup/SKILL.md) 映射真实测试命令后接入，安装插件本身不会配置 Git 或远端门禁。

## 命令入口

显式调用 `$playbook-testing <命令> [参数或自然语言约束]` 时，按 [命令工作流](references/commands.md) 仅执行对应命令。无参数显式调用时展示下面的菜单和当前是否已有策略，不自动初始化或运行测试。自然语言请求仍按下文工作流处理。

| 命令 | 作用 |
| --- | --- |
| `init` | 测试策略与建设，默认接入代理/Git/PR/部署/发布/生产检查 |
| `plan` | 按模块和风险给出具体测试动作、阶段与退出条件 |
| `check [阶段]` | 运行既有阶段，默认 task-finish |
| `fix [阶段]` | 定位失败、最小修复、补回归并复测 |
| `doctor` | 只读检查策略、hook 包装脚本和证据状态 |
| `hooks [status/on/off]` | 查看或切换当前项目的代理自动检查 |
| `ci` | 将同一测试策略接入项目 CI 与 PR gate |
| `release` | 验证已部署候选，先冒烟再深入检查 |
| `pin/unpin <命令...>` | 注册/移除项目 `$pt-check` 等独立 skill 入口 |

这些是 skill 内的命令路由，不是 Codex 内置斜杠命令。插件根目录为本文件所在目录的上两级；确定性操作使用该根目录的 `scripts/testing.py`。在终端或 hook 内使用实际解释器与脚本路径，不把 `$playbook-testing` 当 shell 可执行文件。

## 先确定当前任务

- 制定策略：完成仓库发现、验收映射和阶段矩阵；交付可评审的测试方案。
- 接入自动化：在上述基础上实现用户指定的 hook、命令或流水线，并验证实际触发行为。
- 排查或审计：对照实际事件、命令、代码快照和证据找缺口，先复现再做最小修复。
- 执行既有流程：运行适用阶段的既有检查，报告通过项与阻塞项，不借机重建流程。

按需阅读参考资料，不默认加载全部文件：

| 当前需要 | 阅读 |
| --- | --- |
| 给项目各部分与阶段选择测试、补建设并绑定触发点 | [测试动作决策](references/test-actions.md) |
| 决定测什么、何时测、什么算完成 | [核心模型与原文依据](references/core-model.md) |
| 接入编码代理的编辑后、结束前事件 | [代理 hook](references/agent-hooks.md) |
| 接入提交、推送检查 | [Git hook](references/git-hooks.md) |
| 接入 PR、部署、发布与生产验证 | [CI/CD](references/ci-cd.md) |
| 判断结果是否足以放行，或设计结果汇总 | [测试证据契约](references/evidence.md) |

## 1. 发现仓库的真实能力

1. 读取适用的 AGENTS.md、贡献指南、需求和团队完成标准。
2. 识别工作区/包、依赖锁文件、测试目录、配置、构建脚本、现有 CI/CD 和 hook；用文件检索定位，不输出凭据或完整环境变量。
3. 记录已存在的命令、适用目录、运行依赖、测试类型、耗时、报告格式及失败状态。优先复用；缺失项明确标为“未配置”，不猜测命令已经可用。
4. 确定目标代理、Git hook 管理方式与 CI 平台。只有这些信息确实影响实现且无法从仓库获知时，才询问用户。
5. 执行范围内、可重复的基线检查；区分原有失败、本次引入失败及环境问题。现有授权允许时继续独立工作。

## 2. 从验收标准选择测试

- 将可观察的业务行为映射为用例：前置条件、输入/操作、预期结果。覆盖相关的正向、负向、边界及非功能风险；不能只从当前实现反推预期。
- 优先在最低且足够真实的层次验证：纯逻辑用单元测试；组件交互用集成测试；消费者/提供者兼容性用契约测试；关键跨系统路径用 E2E。
- UI、安全、性能、恢复与兼容性测试按变更风险加入。快速集成测试也可以进入开发内循环，不强制固定测试比例。
- 冒烟、区域回归、全量回归是测试计划，可复用相同用例。没有行为影响的文档或格式变更不强制新增行为测试。
- 缺陷修复应尽可能先复现，再补回归验证。TDD 是可选方法，不能在编辑阶段把预期的 Red 状态当成禁止继续开发的理由。
- 需要正式测试计划时，按需使用 [测试计划模板](assets/test-plan.template.md)。轻量任务可直接在任务说明中记录，不创建多余文档。

## 3. 为适用阶段分配检查

| 阶段 | 默认职责 | 失败处理 |
| --- | --- | --- |
| edit：一批修改后 | 受影响的静态检查、单元/快速集成测试 | 反馈并继续实现；合并重复事件 |
| task-finish：准备结束编码任务 | 当前代码的相关回归与适用构建检查 | 继续修复或明确报告未完成验证 |
| commit：提交前 | 暂存快照的快速检查、凭据扫描、相关测试 | 确定性失败阻止提交 |
| push：推送前 | 待推送版本的更广回归、快速集成/契约测试 | 失败阻止推送 |
| pr：PR 创建、更新或合并队列 | 构建、必需测试、安全检查与风险相关验证 | 服务端检查决定能否合并 |
| deployed：候选部署完成 | 预热/就绪、配置和关键路径冒烟 | 失败停止晋级与昂贵后续验证 |
| release：候选版本晋级 | 全量回归及适用的 E2E、性能、恢复、人工验收 | 未满足条件则不晋级 |
| production：发布后与定时运行 | 发布后冒烟、合成监测，按需影子/故障实验 | 告警、暂停流量扩大或按已有策略恢复 |

以上是按需调整的默认模型，不要求把所有阶段一次装进每个仓库。性能长测、浏览器矩阵与环境级故障注入交给专用作业，避免拖慢本地编辑循环。

## 4. 复用命令，薄接入事件

1. 先确认各检查能通过独立命令运行，再让不同 hook 调用相同命令或项目已有的任务入口。
2. 只有重复编排确有需要时才增加共享脚本；不先造通用 runner。平台事件名、JSON 和退出语义按目标平台当前官方文档核对。
3. 增量选择优先使用框架或依赖图。映射不可靠时扩大到所属包或全量；共享库、依赖锁、构建、权限与数据库迁移变更采用更广验证。
4. hook 只处理事件输入、选阶段、调用、归一结果及返回决策。本插件运行时使用 [JSON 策略](../../templates/testing-policy.json) 与 [配置说明](../../docs/configuration.md)；[YAML 策略模板](assets/testing-policy.template.yaml) 只辅助设计，不由执行器加载。空阶段或未配置命令不能通过。
5. 保留现有 hook 链、CI 作业与团队配置。只修改用户指定范围；安装技能不等于授权修改任意仓库、全局 Git 设置或发布线上应用。

## 5. 执行与放行的不变量

- 结果绑定被测快照、测试配置、依赖和环境。代码或相关输入改变后旧结果失效；本地缓存不能代替可信 CI 结果。
- 通过需要必需检查实际完成。缺报告、未运行、零个实际执行用例、全跳过、超时、环境异常均不能默认为通过；明确不适用项记录理由与项目规定的批准。
- 开发中的暂时失败与阶段最终放行分开；已有失败不等于本次回归，也不自动获得合并豁免。
- 失败后定位、最小修复、重跑受影响检查。重试有界并保留首次失败；禁止通过删测试、弱化断言、滥更新快照或降低阈值取得绿色结果。
- 异步 hook 提供反馈；正式门禁等待所需结果。代理结束检查避免递归阻断；无法在任务范围内解决时交付真实阻塞状态。
- 部署先冒烟，再做深入验证。环境级测试有隔离数据、资源清理和终止条件；生产测试遵循已授权的范围与恢复策略。
- 覆盖率、性能阈值、审批和退出条件遵从项目约定；不把原文的百分比例子或团队示例变为通用硬要求。

## 6. 验证接入并交付

在临时分支、工作区或测试环境中验证本次新增的关键路径，避免修改用户真实提交来制造失败：

- 正常检查成功时可进入下一阶段；有真实失败时对应阶段拒绝放行。
- 测试未运行、环境缺失或报告缺失不会被包装成成功。
- 检查后再修改代码时，不会复用旧的通过结论。
- 仅在接入相关模式时验证：暂存快照/推送 ref 正确、代理事件实际触发、CI 汇总覆盖必需检查、部署冒烟失败停止后续步骤。

没有目标环境时，用隔离 fixture 验证可验证部分，明确哪些只是静态核对，哪些尚未实际触发。人工评审与业务签署不能用模型自评替代。

交付说明保持简洁：本次覆盖阶段、文件与命令、实际验证结果、必需检查及尚未验证的配置/权限/环境条件。用户只要方案时不擅自启用 hook；要求接入时持续完成已授权的实现和可运行验证。
