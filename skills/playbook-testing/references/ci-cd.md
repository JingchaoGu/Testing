# PR、部署与发布门禁

init 默认处理这些阶段的接线，详见 [默认阶段接入](default-hooks.md)。保留已有平台与业务作业；GitHub 默认准备 PR 与可复用交付门禁。没有实际 CD、环境或权限时明确待接入，不把模板文件当作已触发。

## PR：可信执行与合并控制

复用已有 CI 平台和项目命令，在干净环境安装锁定依赖、构建、执行必需测试并保存报告。根据变更风险加入契约、真实依赖集成、UI/E2E 或安全扫描；长测按风险放专用作业或发布阶段。

- 对 PR 合并候选运行适用检查，不只验证脱离目标分支的 feature HEAD；记录实际被测 SHA、基线和合并关系。
- 必需检查列表来自经评审的项目策略。策略与测试本身改变也需要相应评审，不能由待验证代码单方面宣布少测即可通过。
- 汇总门禁核对所有预期检查已完成、报告属于同一候选、应执行的测试确实执行。未运行、缺报告、失败、取消、超时、全跳过或环境异常不能转成成功。
- lint、编译、扫描等命令检查可以没有用例数；测试套件必须有实际执行证据。少量合理跳过由项目策略决定，不把“有一个跳过”一律判失败。
- 绑定 required checks 与评审策略，明确绕过权限和紧急流程。仅新增一个 workflow 文件并不代表已启用服务端合并保护。
- 现有授权允许时配置并核对服务端规则；缺权限时完成本地可评审变更，明确列出尚未生效的远端设置，不能宣称门禁已强制执行。

GitHub 的 required checks 可以接受 successful、skipped 或 neutral，因此需要验证必需套件的实际结果。路径过滤不应让必需汇总作业永远不触发；被跳过的可选作业与缺失的必需作业分别处理。[受保护分支说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

使用 GitHub merge queue 时，还需覆盖 `merge_group`，验证实际合并组。按平台文档核对触发条件；不把 PR、push 与 merge queue 事件当成等价。[GitHub 工作流事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

对 fork 或不可信 PR，采用平台支持的最小权限方式运行代码；不要为取到凭据而把不可信代码放进有写权限或生产秘密的事件上下文。

## 部署：先确认可测，再深入验证

对 CI 产生的明确产物及其 digest 部署，不在每次晋级时重新构建另一份产物。记录环境、配置和数据迁移版本。

建议顺序：环境和数据准备 → 部署与预热/就绪 → 配置及核心路径冒烟 → 集成/E2E 与适用验收 → 判定环境晋级。

冒烟失败立即停止依赖它的昂贵验证和流量扩大，保留日志、环境和版本信息。异步作业也必须由编排器等待最终状态后才能晋级。

涉及数据库时，验证适用的迁移、兼容性和恢复路径。测试数据与资源使用项目已有的隔离与清理方式；不能让并发 PR 相互污染。

## 发布：用项目退出条件决定晋级

- 确定候选产物、目标环境、所需回归、非功能指标、缺陷处理条件及人工签署。
- 用接近生产的代表性负载与环境评估性能。保存基线和每轮结果，改变配置后重新测；不能不经测量直接套用统一 CPU 或覆盖率数字。
- 恢复、故障注入、耐久与容量测试按风险和项目计划触发。环境级实验具有隔离范围、超时、资源预算和恢复机制。
- UAT 与产品签署由约定的责任人作出。自动化检查可核对签署记录存在且对应候选，但不能替人签署。
- 在已授权的发布任务范围内执行晋级。只要求建设 hook 或审计流程，不构成实际发布授权；已有发布授权无需再次重复询问。

## 生产验证与缺陷回流

按现有策略进行发布后冒烟、逐步扩大流量、合成监测，按需增加影子比较。使用隔离测试身份和可识别数据；影子请求隔离写入与外部副作用。生产故障注入仅在已授权实验范围内运行。

指标异常时由已有发布策略暂停晋级、告警或恢复；回滚需考虑数据库及外部状态，不假设切回应用版本就能撤销所有影响。

把已确认缺陷或事故转成可复现用例，加入最合适的测试层与后续测试计划，完成“生产反馈 → 回归保护”的闭环。

## 验证重点

验证新增流水线的语法和命令；用隔离作业证明必需失败、缺报告或全跳过不能通过汇总；证明冒烟失败后不执行后续晋级。发布环境不可访问时，明确未验证部署/审批及服务端保护，不用模拟结果代替真实结果。
