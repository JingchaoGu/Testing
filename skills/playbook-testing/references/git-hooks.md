# Git 提交与推送检查

## 保留项目已有接入方式

先检查 Git 目录、`core.hooksPath`、现有 hook 和项目的 hook 管理器。沿用现有方式，保留已有链路；不为一份脚本安装多个管理器或覆盖用户全局配置。项目尚无管理器时选择最小的可分发方式，并在目标操作系统验证 shell、路径、权限与退出状态。

Git 的 `pre-commit` 和 `pre-push` 可通过非零退出状态拒绝操作。本地检查可以绕过，因此不能替代 CI。[Git 官方 hook 文档](https://git-scm.com/docs/githooks)

## pre-commit：检查实际暂存内容

1. 以 Git index 为本次候选内容来源，读取新增、修改、删除和重命名信息，文件名使用支持空字符分隔的处理方式。
2. 快速静态检查和凭据扫描覆盖候选变更；行为测试覆盖受影响逻辑。共享配置或依赖变更时扩大范围。
3. 存在部分暂存时，测试工作区可能测到未提交的修复。优先在干净、隔离的暂存快照运行；若项目已有可靠的暂存快照机制则复用。
4. 无法可靠运行暂存快照时，明确拒绝存在会影响验证结果的未暂存差异，并提示用户整理暂存内容；不能把工作区结果冒充 index 结果。
5. 不默认以 stash/pop、reset、checkout 或自动暂存来整理用户工作区；保留原有暂存、未暂存与未跟踪内容。
6. 检查失败返回非零并说明命令、失败和报告位置。格式化若改变候选内容，需要重新验证新内容，不静默提交另一份快照。

静态工具可只接收暂存文件清单；跨文件测试仍需要完整候选快照。仅检查文件名或是否出现测试文件，不能证明行为覆盖充分。

## pre-push：检查实际要推送的 ref

1. 读取 hook stdin 的全部 ref 更新，包含 local-ref、local-object、remote-ref、remote-object，不能默认永远是当前 `HEAD`。
2. 对每个待推送候选版本选择所属项目的构建、单元回归及快速集成/契约测试；相同候选版本可去重。
3. 处理新分支、删除 ref、多 ref 和非快进更新。删除 ref 没有待测试代码；新分支缺少远端基线时采用可靠目标基线或扩大到全量，不对全零对象做 diff。
4. 候选与当前工作区不同或工作区不干净时，在隔离的候选版本运行；依赖安装使用项目锁文件，不混入本地未提交状态。
5. 无法验证必需候选版本时返回非零并保留未验证原因。禁止通过先推送再后台测试来模拟 pre-push 门禁。

## 验证重点

用临时 Git 仓库和本地 bare 远端即可验证，不需要推送到真实服务：

- 通过可提交/推送，真实失败会被拒绝。
- 暂存版本失败而工作区未暂存修复通过时，提交仍被拒绝。
- 被推送的非 HEAD ref 失败时，推送仍被拒绝。
- 新分支、删除 ref、多 ref 及带空格路径正确处理。
- 原有 hook 仍运行；用户真实工作区状态不受验证影响。

用户只要求 pre-commit 时不顺带接入 pre-push；只验证本次改变的接入范围。
