# 从项目风险决定测试动作

这是 init 和 plan 的决策主线。先确定需要证明什么，再选择测试层次、用例和阶段；已有脚本只是实现手段。新项目没有测试时，应按此流程建议并建设适用测试，不能把“没有现成命令”作为停止理由。

依据 [Playbook 的目标到测试技术映射](https://microsoft.github.io/code-with-engineering-playbook/automated-testing/)、[测试计划](https://microsoft.github.io/code-with-engineering-playbook/automated-testing/test-planning/) 与 [核心模型](core-model.md)。以下阶段/hook 分配是本插件的工程化方案，不是微软发布的统一门禁配置。

## 1. 按模块分析需要证明的行为

从需求、架构和实际代码识别模块及边界。新项目结合已明确的目标架构与当前最小功能，不等所有代码写完才制定测试。每个实际部分至少给出风险、可观察预期、测试动作与理由；正常、错误和边界场景都要考虑。

| 项目部分/风险 | 建议的测试动作 | 需要证明的典型行为 |
| --- | --- | --- |
| 领域逻辑、算法、校验 | 单元测试；适用时属性/参数化测试 | 正常输入、空值、边界、非法输入及业务不变量 |
| API/服务边界 | 请求级集成测试、接口契约验证 | 状态码、响应结构、输入校验、错误语义及兼容性 |
| 数据库/存储/迁移 | 真实存储上的集成测试、迁移验证 | 约束、读写、事务、并发、升级及适用回退；mock 不证明数据库行为 |
| 服务调用、消息/事件 | 消费者/提供者契约、跨组件集成 | 超时、重试、重复消息、幂等、失败隔离及契约兼容 |
| UI/用户操作 | 组件交互、可访问性、关键旅程 E2E | 加载/空/错误状态、输入反馈、键盘操作及用户能完成核心任务 |
| 身份、权限及敏感数据 | 正反向授权测试、静态/依赖/凭据检查 | 未认证、越权、跨租户、敏感信息泄露及已声明安全要求 |
| 构建、配置、部署 | 构建/打包验证、就绪与版本冒烟 | 产物可运行、必需配置正确、依赖就绪、实际部署版本正确 |
| 性能、可靠性及运行 | 按目标选择负载/容量/长期/故障恢复测试、合成探测 | 延迟/吞吐目标、退化与恢复、发布后关键路径持续可用 |

不要为了凑齐表格创建不存在的数据库、浏览器测试或生产环境。对当前不适用的部分写明理由；对架构中计划存在但尚未具备环境的部分，列为待接入并给出依赖、触发阶段和退出条件。纯函数库可以主要使用单元测试，并按交付方式考虑公共接口、打包/导入验证；不能以此推导 Web/API 项目也只需要单元测试。

## 2. 将动作分配到阶段和触发点

下表是选择起点，要按项目规模、风险与运行耗时调整。每个阶段给出该项目的具体动作及 check ID，不能只把同一个 unit 命令机械复制到全部阶段。合理复用同一组用例时说明它在不同阶段验证的快照或范围。

| 阶段 | 应考虑的动作 | 触发与失败处理 |
| --- | --- | --- |
| 需求/设计 | 可测量验收标准、风险、测试数据和退出条件 | plan/init 产出方案；必要的业务/人工签署保持人工责任 |
| edit | 受影响的静态检查、单元和足够快的集成测试 | Codex PostToolUse；给快速反馈，允许 TDD 暂时 Red |
| task-finish | 本次变更相关回归、构建，以及涉及边界的快速集成/契约 | Codex Stop；必需本地检查失败时继续修复或报告未完成 |
| commit | 暂存快照的快速检查、相关测试、适用凭据检查 | Git pre-commit；失败阻止提交 |
| push | 候选 commit 的更广回归、适用构建/集成/契约 | Git pre-push，读取真实 refs；失败阻止推送 |
| pr | 必需构建、单元/集成/契约、安全与风险相关 E2E | CI/合并队列及最终 gate；失败不得合并，远端规则须核实 |
| deployed | 就绪、配置/产物版本和关键功能冒烟 | 部署完成事件；smoke 失败停止后续验证/晋级 |
| release | 关键旅程 E2E/回归，适用性能、恢复、安全和业务验收 | 候选发布门禁；未满足退出条件则不晋级 |
| production | 发布后冒烟、合成监测及适用真实用户指标 | 发布后/定时监控；失败按项目已有策略告警或恢复 |

耗时较长的浏览器矩阵、真实依赖、压力/长期测试交给 CI 或环境作业。说明本地检查通过仍有哪些 PR/发布条件未验证；不能通过删除必需动作来适配 hook 超时。部署及生产测试只在已授权的环境运行。

## 3. 从建议走到可执行门禁

1. init 默认在项目创建或更新 `TESTING.md`，使用 [测试计划模板](../assets/test-plan.template.md) 保留适用内容。plan 只要求建议时可在回复中交付相同矩阵；要求落盘时写入该文件。已有同类测试计划时直接合并，不平行维护两份。
2. 每项动作标明：目标/风险、用例与预期、测试层次、阶段、策略 check ID/命令、触发方式，以及“已落地 / 待接入 / 不适用”和理由。单独记录实际执行结果；“已落地”不等于本轮已经通过。环境未具备时写出恢复条件，不能把它标为通过或不适用。
3. 对当前授权范围内的必需动作补建测试、测试数据/夹具、报告和可重复命令；已有实现匹配目标时复用。仅安装插件或复制配置不能算已建设测试。工具选择服务于风险，不统一强制框架、覆盖率比例或重试取得绿色。
4. 将项目核心阶段写入 `.testing-policy.json` 的 `required_stages`，将每个适用动作的 check ID 纳入对应 stages 数组；检查定义使用真实 argv 和报告。默认考虑 edit、task-finish、commit、push、pr；显式排除或不同交付方式需要记录理由，部署/发布/生产按实际里程碑确定。
5. 核对计划 → 检查实现 → stages → hook/CI 触发点逐项连通。init 默认按 [阶段接入](../../setup/references/default-hooks.md) 覆盖代理、Git、PR 和交付检查，已有 hooks/流水线是接线载体，缺少的才创建并保留现有链路。配置了 pr 检查但没有 CI 触发/required check，不能声称 PR 门禁已生效；本地 Git hooks 不能代替服务端保障。
6. 运行每个适用核心阶段并检查快照、实际用例数和证据；用隔离 fixture 验证必需动作失败时对应门禁拒绝放行。环境级阶段先 smoke。无法验证的触发点和外部审批明确交付为待接入/未验证，不能用 doctor 的配置检查代替执行。

## 4. 后续变更持续调整

每次新增模块、接口、存储、权限、依赖或部署方式时，重新核对受影响行为与风险，并更新 TESTING.md、测试和阶段配置。缺陷修复补必要回归；性能、部署和生产结果回流到后续测试选择。hooks 负责执行所选动作，测试是否充分仍需验收标准、风险分析和适用评审共同判断。
