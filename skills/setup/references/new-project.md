# 从新项目开始

用于目标目录为空、只有说明文件、已有源码但尚未初始化 Git，或上次仅生成了空测试策略的情况。当前目录可以作为新项目目标；不要仅因为没有 Git 或现成测试就要求用户换目录。

## 先确定最少的信息

先读取用户本次请求、会话约定、AGENTS.md、README 和已有文件。已经给出的路径、技术栈、项目用途与范围不重复询问。

如果技术栈或项目用途确实无法确定，集中询问一次：“这个目录准备创建什么项目？请给出技术栈和一个最小功能，或选择 Python / Node.js 测试演示项目。”给出这几个可选方向，等待答案；不要提前创建空策略后就声称初始化完成。用户只想体验测试工作流时，可采用其选定语言的最小演示功能，并明确演示测试不代表未来业务覆盖。

例如，`$playbook-testing init python 创建一个将标签去空格、转小写并去重的工具` 已提供足够信息，应直接继续，不再询问项目路径或是否初始化 Git。

## 创建与接续项目

先按 [测试动作决策](../../playbook-testing/references/test-actions.md) 将目标拆成模块、边界与风险，为各部分选择测试动作并分配阶段，写入 TESTING.md。即使没有代码/现成测试也要交付这份建议；随后实现适用部分。不要把所有新项目都简化为一套单元测试挂满五个阶段。

1. 创建或补齐最小可运行项目、与目标功能对应的实现、真实测试，以及必要的依赖/运行说明。用项目自身的测试框架；不要加入与目标无关的示例业务。已存在源码时复用和补齐，不重建整个项目。
2. Python 的轻量项目可用标准库 unittest 和本插件的 unittest_junit.py，无需为了接入新增第三方依赖。Node.js 可用 node:test 与内置 JUnit reporter；其他技术栈沿用其原生脚手架和报告能力，不强制改成 Python/Node.js。核对本机运行时与依赖是否可用，缺失时报告具体条件。
3. 新项目请求包含在所选目录建立本地 Git 的授权。确认目录没有归属于另一个父仓库；已有父仓库时使用实际根目录或澄清目标，不在父仓库里擅建嵌套 Git。新目录使用 `<python> <plugin>/scripts/setup_repo.py --repo <目标目录> --init-git`；已有仓库省略该参数。保持现有 Git 历史、索引、远端与身份设置，不自动提交或推送。
4. 根据实际项目填写 .testing-policy.json。为适用的 edit、task-finish、commit、push、pr 映射真实检查，JUnit 必须写入 `{report}`。环境级阶段按实际需要配置；不为尚不存在的部署环境填充假检查。
5. 如果目录已经有 .git、.testing-tools 或 .testing-policy.json，先核对内容，接续未完成的部分。空阶段表示尚未接入测试，不表示项目已经完成；保留现有业务文件和用户配置，运行器冲突按 setup 流程评审合并。

Node.js 使用支持该功能的运行时，可以配置 `["node", "--test", "--test-reporter=junit", "--test-reporter-destination={report}"]`。正式参数见 [Node.js 测试报告](https://nodejs.org/api/test.html#test-reporters)。Python unittest 的 argv 例子见 [配置说明](../../../docs/configuration.md)。

## 验证后完成接入

先运行实际测试并核对执行用例、失败状态和报告，再按 setup 启用项目代理检查、安装所需 Git hooks、运行 doctor。用隔离副本或 fixture 检查失败路径，保持用户索引和未提交改动。测试命令明确失败或没有实际执行用例时，保留失败并继续修复，不通过删断言、跳过测试或将测试改标 command 取得通过。

交付时区分三个状态：等待项目选择、项目/测试骨架已创建但验证未完成、真实测试验证及适用 hooks 已接入。信息已经充分时，持续完成后续步骤，不在 `git init` 或复制配置后提前结束。Codex hook 信任仍由用户在 `/hooks` 确认；CI 服务端规则和生产部署不属于本地初始化自动完成的范围。
